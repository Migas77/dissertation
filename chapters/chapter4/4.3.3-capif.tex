\subsection{Secure \acs{API} Exposure via \acs{CAPIF}}
\label{chap:impl:exposure:capif}

Section~\ref{chap:proposal:exposure:capif} established the need for a single governance mechanism responsible for the secure publication, discovery and consumption of the testbed’s network exposure interfaces, identifying \acs{CAPIF} as the standardized framework to fulfill this role. Such a framework is essential to ensure uniform access to the network's capabilities, covering both \acs{NEF} and CAMARA \acsp{API} under a common set of procedures. To implement the standard and integrate it with the existing exposure components, the testbed adopts Open\acs{CAPIF}\footnote{https://ocf.etsi.org}~\mbox{(Release~4.0.0)}, an open source \acs{CAPIF} implementation developed by \acs{ETSI}.

Fully aligned with \mbox{3GPP~TS~29.222~Release~19}~\cite{}, Open\acs{CAPIF}\footnote{https://ocf.etsi.org/documentation/latest/architecture/architecture/} implements the \acs{CCF} \acsp{API} as a series of microservices, one per \acs{API}: Discover, Publish, Events, Invoker Management, Security, Logging, Auditing, Access Control Policy, Provider Management, Routing Info, and Open Discover, all exposed behind an Nginx reverse proxy with \acs{mTLS}. It also provides a Register service that handles user management, registering, authenticating, and managing the users that will interact with \acs{CAPIF} as Invokers or Providers. Additionally, a HashiCorp Vault\footnote{https://www.hashicorp.com/en/products/vault} instance acts as the \ac{CA}, managing and signing all \acs{CAPIF} certificates.

Among the available open source \acs{CAPIF} implementations, Open\acs{CAPIF} was selected for being standard-compliant and actively maintained by \acs{ETSI}, with regular releases tracking the evolution of the specification. It further provides a dedicated codebase for integration with the exposure ecosystem, the Open\acs{CAPIF} \acs{SDK}\footnote{https://ocf.etsi.org/documentation/latest/sdk/sdk\_introduction/}, which streamlines onboarding and interaction with the \acs{CCF} for both providers, publishing their service \acsp{API}, and invokers, e.g. the network applications consuming them. Finally, its architecture aligns with the cloud-native paradigm targeted by the testbed, as all microservices are containerized and packaged as Helm charts, enabling their seamless deployment and lifecycle management alongside the remaining components of the testbed.

\subsubsection{Open\acs{CAPIF} Integration}
\label{chap:impl:exposure:capif:opencapif}

Integrating Open\acs{CAPIF} into the testbed required realizing these procedures on both sides of the exposure chain, for both providers (i.e. \acs{NEF} and CAMARA) and the invokers (i.e. CAMARA and the network application). For the \acs{NEF}, this was expected to be more straightforward, as its built-in \acs{CAPIF} support was a key reason for selecting the \acs{NEF}Sim implementation in the first place. More concretely, the original upstream version of the emulator\footnote{https://github.com/EVOLVED-5G/NEF\_emulator} relied on the EVOLVED-5G \acs{SDK}\footnote{https://github.com/EVOLVED-5G/SDK-CLI/blob/master/evolved5g/sdk.py}, which provides dedicated classes for provider onboarding and \acs{API} publication, invoker onboarding, invocation logging and auditing, service discovery, and OAuth-based authorization. From these, the emulator utilized the provider classes to onboard and publish the MonitoringEvent and AsSessionWithQoS \acsp{API}, logging each invocation to \acs{CAPIF}. Incoming requests were authorized by verifying the signature of the \acs{CAPIF}-issued access tokens (i.e. \acsp{JWT}) with the \acs{CAPIF} server's public key.

This implementation was validated with older Open\acs{CAPIF} versions. However, a closer assessment of the implementation revealed that the \acs{SDK}'s integration had not kept pace with subsequent releases of the framework, resulting in erroneous and inconsistent behavior, for the most recent Open\acs{CAPIF} releases. Thus, this dissertation uses the Open\acs{CAPIF}~\acs{SDK}\footnote{https://pypi.org/project/opencapif-sdk/}, a Python package maintained alongside the \acs{CCF} within the \acs{ETSI}~Open\acs{CAPIF} project and kept compatible with its public releases, to implement provider and invoker procedures in the \acs{NEF}Sim, CAMARA and network application components. This also simplifies the integration process as the testbed grows, since new exposure interfaces, whether \acs{NEF}, CAMARA or even proprietary \acsp{API}, can reuse the same \acs{SDK} functionality instead of reimplementing the \acs{CAPIF} procedures. The same applies to any new network applications that third parties may wish to develop, provided they are built within the Python ecosystem.

Since both the \acs{NEF}Sim and CAMARA interfaces are implemented with Fast\acs{API}\footnote{https://fastapi.tiangolo.com}, a Python web framework for building \acsp{API}, the Open\acs{CAPIF} \acs{SDK} is integrated through two mechanisms provided by the framework, each covering a distinct stage of the procedures described earlier. This approach also ensures the implementation of the \acs{CAPIF} flows remains independent of the testbed deployment environment, supporting development and operation outside the testbed (e.g. in non-Kubernetes environments, using Docker Compose, or in local deployments with a separate \acs{CAPIF} instance), in line with the goal of the corresponding open source repositories. 

Fast\acs{API}'s lifespan events provide a mechanism for defining custom code to be executed during application startup and shutdown, allowing \acs{CAPIF} procedures to be tied to the application lifecycle. At startup, the \acs{NEF}Sim onboards as an \acs{API} provider and publishes its \acsp{API} to the \acs{CCF}, using a \acs{CAPIF} user already created beforehand (an additional step was included in the Open\acs{CAPIF} deployment scripts to create a user for the \acs{NEF}, CAMARA and a third party application). This operation is idempotent, ensuring the \acs{NEF} and its \acsp{API} are registered exactly once, across restarts or multiple instances (e.g. Kubernetes replicas). Symmetrically, at shutdown, the offboarding procedure is executed, automatically unpublishing the corresponding \acsp{API}. However, to prevent the application from deregistering the provider and unpublishing its \acsp{API}, in the case of a multi-replica setup, the offboarding procedure at shutdown is disabled by default. The corresponding implementation is illustrated in Figure~\ref{fig:impl:exposure:capif:nef}.

The CAMARA component extends this behavior, additionally invoking the Open\acs{CAPIF} \acs{SDK} to perform the \acs{API} invoker procedures. This includes onboarding as an invoker and discovering all available \acsp{API} associated with its invoker id at startup. Invoker offboarding at shutdown follows the same rule, being disabled by default. Figure~\ref{fig:impl:exposure:capif:camara} showcases the implementation for the lifespan events. This version differs slightly in structure from the previous one, as \acs{NEF}Sim relies on an older Fast\acs{API} version that does not support the lifespan parameter.

The \acsp{URL} of the discovered \acsp{API} are subsequently resolved from the information obtained during onboarding and discovery, without additional \acs{CAPIF} calls. As illustrated in Code Block~\ref{code:impl:exposure:capif:discover}, the \texttt{discover\_nef\_url} function identifies the appropriate endpoint based on the \acs{API} name, resource name, and \acs{HTTP} operation. A fallback URL is provided for when \acs{NEF}'s \acs{CAPIF} authentication and authorization is disabled. The network application also adopts a similar invoker logic. All three implementations rely on separate \texttt{capif\_invoker} and \texttt{capif\_provider} singletons and helper functions, each built around the Open\acs{CAPIF} \acs{SDK} objects. The remaining \acs{CAPIF} procedures occur on a per-request basis and are therefore handled by components that intercept each request, on the provider side for incoming requests and on the invoker side for outgoing ones.

On the provider side, access token validation is implemented as a Fast\acs{API} dependency, i.e. a reusable function the framework resolves and executes before each path operation. This dependency is responsible for extracting the bearer token from the \texttt{Authorization} header and validating it against the \acs{CCF} public key obtained during provider onboarding, as depicted in Figure~\ref{code:impl:exposure:capif:tokenvalidation}. Requests with missing, expired or out-of-scope tokens are rejected by the dependency before the path operation is executed, returning \texttt{401 Unauthorized} when the token is absent, malformed or expired, and \texttt{403 Forbidden} when a valid token does not grant access to the requested \acs{API}.{\color{blue} Not all of this is currently implemented, out of scope tokens are not covered currently} By concentrating token validation in a single dependency, the route handlers of \acs{NEF}Sim and of the CAMARA \acsp{API} remain agnostic to the \acs{CAPIF} integration, allowing developers to focus solely on each \acs{API}'s functional logic, with the same dependency being reused across all \acs{API}.

On the invoker side, the CAMARA (and the \acs{PoC}) consume the \acs{NEF}Sim (and CAMARA) \acsp{API} through an \texttt{httpx} client configured with a custom authentication class, which preemptively verifies the expiry of the current access token and attaches it to the request as a bearer token. If the token is deemed expired or the \acs{NEF} responds with \texttt{401 Unauthorized}, possible in near-expiry scenarios, the class requests a new token from the \acs{CCF}, retrying the invoker request at most once. This way, token acquisition and renewal are also transparent to the code issuing the requests.

Lastly, to establish secure communication between the two roles, the provider enforces \acs{mTLS}, which requires both the client (invoker) and the server (provider) to verify each other's identity using X.509 digital certificates before data exchange begins. This is achieved through an Nginx reverse proxy, one placed in front of each \acs{CAPIFAEF}, i.e. \acs{NEF} and CAMARA, as depicted in Code Block~\ref{code:impl:exposure:capif:nginx}. The configuration relies on three certificate-related directives to establish the \acs{HTTPS} connection: \texttt{ssl\_certificate} and \texttt{ssl\_certificate\_key} hold the \acs{CAPIFAEF}’s own certificate and private key, presented to the invoker during the handshake to prove the server's identity, while \texttt{ssl\_client\_certificate} contains the root certificate of the \acs{CCF}, acting as the \ac{CA}, against which the certificates presented by invokers are validated. Plain \acs{HTTP} requests are automatically redirected to their \acs{HTTPS} counterparts, with requests presenting an invalid client certificate being rejected with \texttt{403 Forbidden}, rather than Nginx's default \texttt{400 Bad Request}. The \texttt{proxy\_pass} directive then forwards the incoming requests to the corresponding backend service, including the \acs{URL}-encoded client certificate in the \texttt{X-SSL-Client-Cert} header.

\begin{listing}[htbp]
\begin{minted}{nginx}
server {
    listen 80;
    server_name _;
    return 301 https://$host:443$request_uri;
}

server {
    listen 443 ssl;

    ssl_certificate         /etc/nginx/provider-certs/provider/aef-1.crt;
    ssl_certificate_key     /etc/nginx/provider-certs/provider/AEF-1_private_key.key;
    ssl_client_certificate  /etc/nginx/provider-certs/provider/ca.crt;
    ssl_verify_client       optional;

    location / {
        if ($ssl_client_verify != SUCCESS) {
            return 403;
        }
        proxy_set_header X-SSL-Client-Cert $ssl_client_escaped_cert;
        proxy_pass http://backend:80/;
    }
}
\end{minted}

\end{listing}

All these certificates required for mutual authentication, for both roles, are generated and provided by Open\acs{CAPIF} as part of the onboarding process. This ensures that only invokers holding certificates issued by the trusted \acs{CAPIF} instance can establish a secure connection with the provider. It also prevents unauthorized entities from impersonating legitimate invokers or providers, that are actually registered with the \acs{CCF}, mitigating the risk of man-in-the-middle attacks. {\color{blue}point out insecure behavior of sdk on first login without verify=true}

Integrating \acs{CAPIF} and \acs{mTLS} into the authentication and authorization process also required changing the deployment \acs{IaC} manifests, including creating the Nginx Docker image~\footnote{\color{blue}add link nginx conf} and adapting the \acs{NEF}Sim docker compose~\footnote{\color{blue}add link NefSIM docker compose}, and the Helm charts of the \acs{NEF}Sim~\footnote{\color{blue}add link NEFSim helm chart}, CAMARA\footnote{\color{blue}add link CAMARA helm chart} and network application\footnote{\color{blue}add link PoC helm chart} components. Moreover, since the aforementioned certificates are only obtained by the Fast\acs{API} application during startup, the Nginx container is deffered from starting until the certificates are available through a helper script (init container on Kubernetes) or compose's \texttt{depends\_on} clause.
