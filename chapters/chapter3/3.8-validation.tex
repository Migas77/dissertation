\section{Validation}
\label{chap:proposal:validation}

The orchestration of this service chain is merely one step of the experimentation process, establishing the underlying environment for the evaluation of vertical applications. This evaluation must verify that the application functions as intended and effectively utilizes the exposed \acs{5G} capabilities, just deployed as services. However, these two aspects cannot be meaningfully assessed in isolation, since the observed behavior of a network application results from the interplay of multiple factors: its internal logic, how it interacts with the network through the available exposure capabilities, and ultimately the network conditions and capabilities that are actually delivered by the \acs{5G} system as a result of these interactions.

The testbed should therefore provide experimenters with the evidence required to account for these diverse factors and validate the application by correlating observability data (e.g. metrics, logs) collected at the various points of the experimental chain: the application, the exposure layer constituted by the \acs{NEF} and CAMARA services, and the underlying 5G network. For example, when an experimenter orders a network slice, the provisioned slice should deliver the throughput and latency expressed by the attributes of the ordered \acs{NEST}. Verifying these conditions requires comparing the requested \acs{QoS} values with the metrics collected for the experiment, including those obtained through active probing.

Similarly, the same principle should extend to the testbed's exposure interfaces. Changes in \acs{QoS} requested through its \acsp{API}, such as the \acs{NEF} AsSessionWithQoS and the CAMARA \acs{QoS} \acsp{API}, should be reflected in the throughput observed for the target \acs{UE} and be observable using the monitoring capabilities offered by the testbed. The values obtained through the analytics interfaces, i.e. the \acs{NEF} AnalyticsExposure and the CAMARA Connectivity Insights Subscriptions \acsp{API}, should, in turn, be consistent with those reported by these monitoring mechanisms, thereby confirming that the analytics exposed to external applications accurately reflect the actual network conditions experienced by the \acs{UE}. These interactions can only be validated by examining the entire request flow. This includes verifying that the requests issued by the application align with the resulting downstream requests generated by the exposure layer, as well as with the corresponding responses. Such examples include requests from CAMARA to the \acs{NEF}, or from the \acs{NEF} to other internal components that may be responsible for fulfilling its capabilities within the testbed, such as a metrics repository. The time taken by the network to fulfill each request, e.g. enforce a \acs{QoS} change, should also be measured, decomposed by each component on the request path.

However, validating the application under nominal network conditions is not sufficient. Experimenters must be able to deliberately induce the adverse or changing conditions the application is expected to withstand. This can be done indirectly, by emulating the network's responses through the exposure layer, or directly, by altering the behavior of the network itself. Emulating responses such as analytics values, events or the outcome of \acs{QoS} requests allows different scenarios to be simulated without reproducing them in the actual network. By contrast, stress testing the network with competing traffic, for instance through the testbed's active probing mechanism, reproduces the scenario in the actual network, effectively degrading the \acs{QoS} of the provisioned slice and reducing the bandwidth available to the application. The application may then react: a video streaming service, for example, might lower its stream resolution or request a different, possibly higher-priority, \acs{QoS} profile. Moreover, since the instant at which the new \acs{QoS} profile is requested through the exposure interfaces is known, the network metrics collected before and after that instant can be contrasted to assess whether the request was effectively enforced and if it contributed towards improving the application's behavior. By correlating, along a common timeline, these metrics, the requests issued to the network and the application's behaviour, the testbed validates whether each request was effectively enforced, supporting a rigorous evaluation of how the application adapts to changing network conditions.

Both approaches are complementary: emulation allows the application's logic to be exercised under controlled and reproducible scenarios, including those that are difficult to induce in the actual network, whereas tinkering with the network itself validates the application end-to-end under the conditions effectively delivered by the \acs{5G} system. In this way, the testbed allows vertical developers to assess the functional correctness of their applications and their resilience to network variability, based on real evidence from the provisioned services and the mobile network.
