\section{Secure \acs{API} Exposure via \acs{CAPIF}}
\label{chap:proposal:capif}

The \acs{NEF} and CAMARA components described in the preceding sections provide the mechanisms necessary to expose network capabilities to third parties. Together, they provide developers with the interfaces required to interact with the underlying \acs{5G} infrastructure, leveraging it to build network applications. Nevertheless, a standardized mechanism for the secure discovery, exposure, and consumption of these northbound \acsp{API} is yet to be defined. This is particularly relevant in the context of a testbed, where such components must be shared between multiple independent clients and, consequently, cater to the needs of multiple network applications.

The \acf{CAPIF}, by \acs{3GPP}~\cite{ETSI_CAPIF_TS_123_222_V18_4_0}, addresses this problem by defining a common framework for the exposure of northbound \acsp{API} in \acs{5G} systems, as detailed in Section \ref{sota:initiatives:CAPIF}. It introduces a set of roles, namely the \acs{API} Provider, \acs{API} Invoker and \acs{CAPIF} Core Function, along with the procedures for \acs{API} publishing, discovery, and access control. \acs{CAPIF} was designed within the domain of \acs{3GPP} with the goal of protecting its northbound interfaces, such as \acs{SCEF} and \acs{NEF} northbound \acsp{API}. However, in practice, several works in the research community have extended the usage of \acs{CAPIF} beyond its original scope, treating it as a general-purpose \acs{API} gateway with authentication and authorization capabilities, and leveraging it to protect other \acsp{API} defined by other \acsp{SDO} or consortiums, such as CAMARA \acsp{API}~\cite{PathwayNaaSCAMARA}. \review{inconsistent with CAPIF website (and my introduction on Section \ref{sota:initiatives:CAPIF}) - it says any 3gpp or non-3gpp and explicitly states CAMARA. This dissertation follows the same interpretation. \acs{CAPIF} is used to expose and protect both \acs{NEF} and CAMARA \acsp{API}, with the explicit understanding that this represents an extension beyond \acs{CAPIF}'s original intent. Under this model, (i) \acs{CAPIF} acts as a unified secure exposure layer for all northbound \acsp{API} in the testbed; (ii) both the \acs{NEF} and CAMARA \acsp{API} act as \acs{API} providers exposing interfaces to be consumed by network applications, which operate as external API invokers; and (iii) each CAMARA \acs{API} additionally assumes the role of an internal \acs{API} invoker, interacting with \acs{NEF}'s \acs{API} to deliver its services from inside the network's trust domain.

As a result, rather than requiring separate onboarding, discovery, and authentication procedures for each \acs{API} suite, a single \acs{CAPIF} integration point consolidates these concerns regardless of whether the underlying \acs{API} is a \acs{3GPP} \acs{NEF} interface or a CAMARA abstraction. This significantly reduces integration complexity and aligns with the testbed's objective of providing a developer-friendly environment for the development and validation of network applications.
