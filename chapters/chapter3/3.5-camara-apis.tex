\section{CAMARA \acsp{API} Integration}
\label{chap:proposal:camara}

The prior section established how the testbed can autonomously collect network metrics and expose them through the \acs{NEF} \textit{AnalyticsExposure} \acs{API}, making them accessible to third parties. Network application developers who wish to incorporate analytics and adaptive network behavior into their applications must interact with the network through this and other \acs{NEF} interfaces. This can be accomplished in one of the following ways: (i) interacting directly with the \acs{NEF} northbound \acsp{API}, which requires familiarity with the \acs{3GPP} ecosystem, specifications and data models, imposing a significant burden on developers lacking the necessary telco expertise; or (ii) interacting with the network through CAMARA \acsp{API}, which abstract the complexity and underlying interactions with the \acs{NEF} and any other components contributing to the offered service, through a user-friendly interface.

The CAMARA initiative focuses on standardizing \acsp{API} at the northbound of the network, defining what capabilities are exposed and how application developers can interact with them to easily integrate network behavior into their applications. However, the southbound realization of those northbound \acsp{API}, i.e. their internal implementation, is deliberately left to each network operator. Nevertheless, \acs{GSMA} produces guideline documents, such as \textit{\acs{NBI} \acsp{API} Realisation in the \acs{SBI}}~\cite{gsmaNbiRealization}, describing how CAMARA \acs{API} operations can be realized through the \acsp{API} and procedures available in the operator's network, including via \acs{NEF} northbound interfaces.

The CAMARA \acsp{API} integration proposed in this section is derived from this reference realization model, mapping CAMARA operations to the corresponding \acs{NEF} interactions. The following subsections detail the adopted \acs{NBI} realization procedure for the following CAMARA \acsp{API}: \textit{Application Profiles} and \textit{Connectivity Insights Subscriptions}.

\subsection{Application Profiles \acs{API}}

The \textit{Application Profiles} \acs{API} enables network application developers to share essential information about their applications with the network and other CAMARA \acsp{API}, informing their behavior and decisions~\cite{CAMARAApplicationProfiles}. The \acs{API} focuses on defining network quality thresholds and compute resource requirements needed by the application, which naturally translate into a broad range of use cases. Across media streaming, online gaming, and video conferencing, services can benefit from the use of such an \acs{API} to verify network conditions (e.g. bandwidth, latency, jitter, packet loss) against the desired requirements and dynamically adapt their behavior accordingly. The same profile may also assist network operators in allocating resources and defining \acsp{SLA}, based on the application’s defined needs.

The following section details how the \textit{Application Profiles} \acs{API} can be implemented according to the testbed's architecture, describing the sequence of interactions performed from the moment a request reaches the CAMARA \acs{API}.

\subsubsection{\acs{NBI} Realization}

Figure~\ref{fig:flow:CAMARAapplicationProfiles} illustrates the \acs{NBI} realization for the \textit{Application Profiles} \acs{API}, adapted from the \acs{GSMA} reference model~\cite{gsmaNbiRealization}. The \acs{API} exposes all the endpoints necessary to perform all \acs{CRUD} operations on an Application Profile~\cite{CAMARAApplicationProfilesRelease}. An Application Profile, expressed by the \texttt{ApplicationProfile} schema, defines application thresholds provided for network quality, including packet delay budget, minimum downstream and 
upstream rates, packet error loss rate and jitter, as well as compute resource requirements, such as target minimum \acs{CPU}, memory and \acs{GPU} specification.

The sequence diagram focuses on the application profiles creation procedure. The \acs{AF}, e.g. a network application, submits a POST request to the CAMARA \acs{API} endpoint specifying the profile application requirements through the \texttt{ApplicationProfileRequest} record~\cite{CAMARAApplicationProfilesRelease}. On success, CAMARA stores the profile on a local repository and returns the created resource identified by a unique profile identifier. This identifier will subsequently be referenced/used in all further \acs{API} operations (retrieval, update and deletion), or by any other CAMARA \acsp{API} that consume the profile. Throughout this workflow, there is no interaction with the \acs{NEF} or the \acs{5GC}. This emphasizes the role of the \textit{Application Profiles} \acs{API} as a management interface over a shared profile repository, storing requirement declarations that other CAMARA \acsp{API} and network systems may reference/use to make their own decisions, as is the case of the \texttt{Connectivity Insights Subscriptions} \acs{API}, discussed in the following section.
